# Семантика протоколов v0

Sandbox API реализован в CP1-04; клиентский API реализован в CP1-06: [границы](../docs/client-gateway.md). Ограничения текущего runtime: [сандбокс](../docs/sandbox.md). JSON Schema проверяет форму одного сообщения. Состояние, полномочия, дедупликацию и последовательность событий проверяет сервер.

## Транспорт

Оба сервиса принимают JSON `POST /v0/requests`. Поле `type` выбирает операцию — это небольшой HTTP RPC, не REST API. Тело запроса и JSON-ответ проверяются соответствующей схемой и разрешённым направлением: сервер не принимает сообщения ответа как команды.

`events.subscribe` отправляется отдельным `POST /v0/events`; ответ — `text/event-stream`. Клиент читает поток HTTP самостоятельно (CLI сейчас, desktop позднее), поэтому не зависит от браузерного EventSource. Для reconnect отправляется новый запрос с `after_event_id`. Поле SSE `id` равно JSON `event_id`, поле SSE `event` равно JSON `type`, `data` — JSON-сообщение одной строкой. Heartbeat-комментарий `: ping` каждые 15 секунд не является JSON-событием.

Gateway требует `Authorization: Bearer <client-token>` на каждом запросе, включая connect, события и скачивание артефакта. Manager требует отдельный сервисный токен харнеса; этот API недоступен клиенту и сандбоксу. Токены не входят в JSON или URL. Между машинами используется TLS либо защищённый туннель; локальный HTTP допустим для разработки.

`GET /v0/artifacts/{artifact_id}` возвращает неизменяемый tar-архив из collect, `Content-Type: application/x-tar`, `Content-Length` и SHA-256 из ответа collect. В gateway доступ проверяется по владельцу сессии, в manager — по сервисному токену. Время скачивания ограничено клиентом 120 секундами. Неизвестный/недоступный артефакт — 404. Ошибка до начала передачи возвращается как JSON error; после начала — разрыв потока, клиент обязан проверить размер и хеш.

## Запрос и время

- `request_id`: уникальный идентификатор запроса, например UUID; назначается отправителем. Ответ содержит тот же id. Ошибка разбора JSON может иметь request_id=null.
- `server_epoch`: идентификатор текущего старта принимающего сервиса, возвращаемый connect. У gateway и manager разные epoch. Все запросы, кроме connect, обязаны предъявлять актуальный epoch.
- `expires_at`: Unix time в целых секундах UTC — последний момент, когда запрос разрешено принять. При новом запросе требуется `now < expires_at <= now + 3600`; часы синхронизированы. Старый запрос никогда не исполняется заново после истечения дедупликации.
- `timeout_s`: 1…1800 секунд. Для синхронных операций — максимальное время обработки; для run.start и exec — бюджет всего запуска/команды после принятия; для подписки — длительность соединения. Повтор не перезапускает таймер. Внутренние операции получают не больше оставшегося бюджета родительского запуска.
- Рекомендуемые значения: connect/status/cancel — 10 секунд, provision/collect/release — 120, exec — 120, run.start — 180, stream — 60. После истечения stream клиент переподключается; агент продолжает работу.

HTTP 200 — успешная синхронная операция/состояние; 202 — run.accepted, exec.accepted и принятие cancel (даже если already_terminal). Ошибки: 400 invalid_request/unsupported_version, 401 unauthorized, 404 not_found, 409 conflict/idempotency_conflict/stale_epoch, 410 expired_request/cursor_expired, 504 timeout, 503 sandbox_unavailable. Ошибки команд после принятия exec передаются в финальном результате, а не вторым HTTP-ответом.

## Клиент ↔ gateway

| Запрос | Ответ | Поведение |
|---|---|---|
| connect | connected | проверить токен, вернуть epoch и пределы протокола |
| session.create | session.created | выделить сессию, проверить pair_id и источник workdir, подготовить sandbox |
| run.start | run.accepted | создать run_id и trace_id, начать агентный цикл |
| run.get | run.state | получить queued/running/cancelling/terminal; у terminal есть result |
| run.cancel | run.cancelled | запросить остановку, статус cancelling или already_terminal |
| session.collect | session.collected | получить артефакт /work через manager; только без активного run |
| session.close | session.closed | остановить активную работу, release sandbox, подтвердить очистку |
| events.subscribe | SSE | события run.started/tool.started/tool.finished/run.result |

Сессия принадлежит principal из токена. Чужая сессия возвращает 404. Одна активная задача на сессию; вторая — 409 conflict. Разные сессии имеют независимые workdir. История диалога сохраняется между run одной сессии.

Состояния сессии: ready → running → ready; закрытие ready/running → closing → closed. run: queued → running → terminal; из queued/running возможен cancelling → terminal. Терминальный run.result содержит completed/failed/cancelled/timed_out. completed означает завершение агентного цикла, а не прохождение БАФ: качество решает check.py.

Gateway сохраняет один логический run.result на run_id. `run.get` возвращает его копию, не создаёт новое событие. Завершённую сессию нельзя использовать для нового run. Повтор close возвращает session.closed. idle TTL — 30 минут без активного run; после истечения gateway закрывает сессию с очисткой. Пока run активен, действует его timeout.

## Харнес ↔ sandbox-manager

| Запрос | Ответ | Поведение |
|---|---|---|
| connect | connected | получить epoch manager |
| provision | provisioned | подготовить /work и контейнер, вернуть sandbox_id |
| exec | exec.accepted | принять operation_id и команду |
| operation.get | operation.state | running/cancelling/terminal, последний результат |
| cancel | cancel.accepted | остановить дерево процессов операции |
| collect | collected | создать архив /work только при отсутствии активной операции |
| release | released | отменить работу, удалить контейнер, mount и временные ресурсы |
| events.subscribe | SSE | exec.output и один логический exec.result на operation_id |

Не более одного exec на сандбокс одновременно. Operation_id выбирает харнес и связывает с tool call; request_id идентифицирует доставку запроса. Повтор operation_id с той же командой и бюджетом возвращает исходное принятие/состояние; с другими параметрами — idempotency_conflict. Result доступен через operation.get.

Инструменты:

- `RunCommand`: argv без автоматического shell; `cwd` относительно /work (`.` — корень). Shell используется явно через argv, например `["sh", "-c", "..."]`. Рабочая директория не является защитой сама по себе — изоляцию обеспечивает контейнер.
- `ReadFile`: путь относительно /work; до 1 MiB, содержимое в content_base64, exit_code=null.
- `WriteFile`: путь и content_base64 до 1 MiB после декодирования; создаёт/заменяет файл, родительский каталог должен существовать; результат без содержимого и exit_code=null. В режиме ro запись запрещена.

Base64 позволяет не терять cp1251/CRLF в Б4.3. Файлы больше предела возвращают ошибку file_too_large, а не незаметно обрезаются. Manager обязан проверять декодированный размер и корректность base64.

Пути не абсолютные, не содержат `..`, обратный слеш и NUL. Дополнительно manager безопасно разрешает путь и симлинки: JSON Schema не защищает от symlink/TOCTOU. Служебные файлы харнеса лежат вне /work; политика защиты .git через mount остаётся отдельной задачей ЧП2.

stdout/stderr представлены UTF-8 с заменой невалидных байтов, ограничены каждый 65536 символами в финале; output-события — куски до 4096 символов. После достижения общего лимита поток продолжает дренироваться без накопления; truncated=true. У RunCommand success — exit_code=0, ненулевой код — failed/command_error; при завершении сигналом — 128+signal. При невозможности получить код — null. ReadFile/WriteFile возвращают stdout/stderr пустыми. Эти соответствия операции и результата проверяются runtime-тестами.

`workdir={kind, source_id, mode}` — серверная ссылка, не произвольный host path. В ЧП1 fixture source_id выбирается из зарегистрированных фикстур; копируется только fixture, без чекера. mount зарезервирован для ЧП2: до реализации сервер возвращает unsupported_workdir_source. Регистрацию удалённого mount добавим отдельным контрактом. Pair_id также выбирается из серверного реестра конфигураций.

Collect возвращает artifact_id/size_bytes/sha256. В CP1-04 дополнительно требуется отсутствие фоновых пользовательских процессов; иначе 409 background_processes. Архив содержит только обычные файлы и каталоги /work, без абсолютных путей, `..`, ссылок и special files; небезопасное содержимое вызывает ошибку. Лимит архива — 64 MiB для v0, превышение явно отклоняется. Чекер получает безопасно распакованную папку вне агентской среды. Release удаляет и артефакты, поэтому раннер скачивает их до release/close; в finally всё равно очищает ресурсы. Повтор collect с тем же request_id возвращает тот же неизменяемый snapshot.

## Идемпотентность, события и restart

Для POST /requests ключ дедупликации — principal + server_epoch + request_id; сравнивается JSON-структура payload, порядок ключей не важен. Повтор той же структуры не выполняет действие снова, возвращает ранее сохранённый HTTP-ответ. Другая структура под тем же ключом — 409. Пока первый запрос выполняется, повтор может ждать завершения сериализованной операции (gateway CP1-06) либо получить 409 request_in_progress с retry=same_request (manager); после задержки допустим тот же запрос. Запись о запросе хранится минимум до expires_at, а о run/operation — до конца жизни ресурса + 3600 секунд. Проверка epoch/истечения идёт до выполнения нового действия. Принятие операции и фиксация ключа должны быть атомарными в пределах процесса.

У подписки нет побочного действия: повтор подписки создаёт новый поток с указанного курсора. Event_id — возрастающее целое отдельно на сессию/sandbox. after_event_id=0 означает с начала. Хранятся последние 10000 событий за 3600 секунд; недоступный старый курсор — 410 cursor_expired, будущий — 400 invalid_cursor. Тогда клиент запрашивает состояние run/operation. Terminal result хранится независимо от кольцевого буфера событий до 3600 секунд после закрытия ресурса. При отсутствии новых событий идут heartbeat; окончание подписки по её таймауту нормально.

«Ровно один result» — один сохранённый финальный результат операции, а не гарантия однократной сетевой доставки. После reconnect тот же event_id может прийти повторно; получатель его дедуплицирует.

В гонке cancel/завершение первое атомарно зафиксированное терминальное состояние побеждает. Cancel после финала возвращает already_terminal. Cancel принят — ещё не означает, что процессы уже остановлены: финал cancelled записывается после подтверждённой остановки дерева. В CP1-04 cancel/timeout останавливает весь контейнер: временная /work теряется, новые exec/collect запрещены, доступны operation.get/events/release. Неудачная очистка — sandbox_error, ресурс считается требующим cleanup, released не возвращается до подтверждённого освобождения.

v0 хранит состояние в памяти и не обещает восстановление операций после restart. Новый epoch отклоняет старые запросы, клиент не повторяет их с новым epoch автоматически. Старый результат может стать неизвестным; это transport_error/unknown_outcome, а не выдуманный success. Перед переходом в ready сервисы согласуют epoch зависимостей, manager удаляет оставшиеся ресурсы проекта по меткам. Неожиданная смена epoch зависимости завершает затронутые run ошибкой. Межпроцессная гарантия сохранности результата потребует durable-хранилища в следующей версии.

## Ошибки и ретраи

| Класс | Пример | Действие |
|---|---|---|
| protocol_error | неверная версия, путь, токен, конфликт | исправить запрос; never, кроме request_in_progress |
| command_error | ненулевой exit, файл отсутствует | вернуть наблюдение модели; автоматического повтора нет |
| timeout | превышен бюджет | остановить дерево; query_status, не запускать команду снова |
| sandbox_error | контейнер/daemon недоступен | query_status, остановить run при неизвестном исходе |
| transport_error | разрыв HTTP | запросить состояние; не повторять side effects вслепую |

Transport_error обычно создаёт отправитель локально: недоступный сервер не может прислать собственную сетевую ошибку. Поле retry — инструкция восстановления, не обещание успеха. При потере ответа до получения run_id можно повторить тот же запрос с тем же request_id/epoch в его временном окне. Нельзя менять expires_at под прежним request_id. После истечения окна неизвестный исход требует разбирательства, а не повторного запуска.

Токены, ключи провайдера и произвольные env-переменные не входят в инструменты или события. Закрытые схемы помогают отсечь лишние поля, но утечки через stdout/логи отдельно проверяются canary-тестами.

## Уточнения реализации CP1-04

Manager использует один внутренний сервисный principal (общий токен harness/manager), восстанавливает epoch только для своего API; согласование epoch зависимостей харнесом относится к CP1-05. Размер тела запроса ограничен 2 MiB. Одновременно допускается максимум 8 сандбоксов, до 1000 операций на сессию. Неизвестный mount source отклоняется. Полная политика прав клиента реализуется с gateway.

## Метаданные БАФ (CP1-07)

Необязательные поля v0: session.created.pair_sha256 — SHA-256 канонического JSON конфигурации выбранной пары; run_result.model — фактический идентификатор ответа модели или null, run_result.mode — real/replay. Новые клиенты раннера требуют эти метаданные для проверки пары и воспроизводимого отчёта; старые примеры без полей остаются валидны.
