# Сандбокс CP1-04

Статус: операции sandbox-протокола реализованы и проверены на Docker. Агентный цикл описан в [harness.md](harness.md); клиентский API реализован в CP1-06: [gateway](client-gateway.md). Локальный сервер: [server.md](server.md).

## Попробовать

```bash
make up
make demo-sandbox
make test-sandbox
make test-server
```

Демонстрация запускается внутри контейнера harness и по HTTP вызывает manager: connect → provision → exec → operation.get → collect → release. Команда читает порт из config/app.yaml, пишет answer.txt, затем ReadFile возвращает `8137`. Это запрограммированный сценарий без LLM, он не засчитывается как прохождение БАФ парой «харнес + модель».

`make test-sandbox` выполняет 18 интеграционных сценариев против реально запущенного manager. Каждый создаёт новые контейнеры и освобождает их в tearDown. Внешняя сеть и модель не нужны. Проверки включают квоту /work и ограниченное создание процессов внутри cgroup; сервер должен быть запущен заранее.

`make test-lifecycle` отдельно перезапускает сервер, проверяет SIGKILL/restart и `compose down -v`. Запускать на dev-проекте без рабочих сессий: команда откажется стартовать, если уже есть динамические сандбоксы. После успешного теста сервер снова работает.

## Как устроено

```text
harness (сервисный токен из read-only volume)
    → HTTP JSON / SSE → sandbox-manager
    → Docker Engine API через Unix socket
    → отдельный контейнер с /work (tmpfs)
```

- [app.py](../services/sandbox-manager/app.py): HTTP, проверка сервисного токена, ограничения тела запроса, SSE и скачивание артефакта.
- [manager.py](../services/sandbox-manager/runtime/manager.py): provision/exec/collect/cancel/release, состояние операций, дедупликация, таймеры и очистка.
- [docker_api.py](../services/sandbox-manager/runtime/docker_api.py): минимальный HTTP-клиент Docker Engine API v1.45 через Unix socket, чтение stdout/stderr из мультиплексированного потока.
- [tools.py](../sandbox/tools.py): RunCommand/ReadFile/WriteFile внутри сандбокса; manager никогда не выполняет пользовательские команды на своём хосте.
- [seed.py](../sandbox/seed.py): установка доверенной фикстуры до пользовательских команд.
- [collect.py](../sandbox/collect.py): ограниченный tar-архив обычных файлов, без ссылок и special files.
- [idle.py](../sandbox/idle.py): PID 1 сандбокса, ожидает работу и собирает завершившиеся дочерние процессы.

Compose собирает пятый образ через служебный `sandbox-image`: этот контейнер сразу выходит с кодом 0. Это ожидаемо, он нужен для сборки образа до старта manager; рабочие сандбоксы создаются динамически.

## Граница доверия

Manager — единственный сервис с Docker socket; он работает от UID 0 для доступа к сокету без ручной настройки группы хоста. Socket фактически даёт полномочия root на хосте, поэтому manager считается доверенным компонентом. Решение и альтернативы: [ADR-0002](adr/0002-sandbox.md).

Пользовательские команды всегда исполняются от UID/GID 10001:10001, без socket, серверных ключей, кода manager и auth-volume. При инициализации ro-фикстуры manager один раз запускает фиксированный seed-скрипт от UID 0 внутри контейнера; до этого пользовательский exec недоступен. Capabilities остаются сброшенными. После установки файлы принадлежат root, читаются пользователем, но не меняются им. В rw-режиме seed и пользовательские команды работают от UID 10001.

Сервисный токен генерируется manager при первом старте и хранится в Docker volume `runtime-auth`. Manager монтирует его rw, harness — ro; gateway, llm-proxy и сандбоксы его не получают. Нет фиксированного токена в исходниках и нет публикации manager-порта на хосте. Проверка токена применяется к запросам, событиям и артефактам. Health endpoints не требуют токена.

В запросах нельзя выбрать image, host path, Docker flags, environment или UID. Источник /work — allowlist: `B1_1` (только курсовая fixture) и `empty`. Чекер не копируется. `kind: mount` пока возвращает unsupported_workdir_source.

## Ограничения ресурсов

| Что | Значение по умолчанию | Реализация / проверка |
|---|---|---|
| CPU | 1 CPU | NanoCpus; проверяется cpu.max в cgroup |
| RAM | 256 MiB | Memory, MemorySwap равен Memory (без дополнительного swap); проверяется memory.max |
| Процессы | 64 | PidsLimit; тест получает EAGAIN при достижении лимита, затем убирает детей |
| /work | 64 MiB | отдельный tmpfs; тест заполнения получает ENOSPC |
| /tmp | 16 MiB | tmpfs, noexec, nodev, nosuid |
| /dev/shm | 1 MiB | ShmSize |
| Команда | min(timeout_s, SANDBOX_EXEC_TIMEOUT_S), по умолчанию 120 с | timer + остановка контейнера; отдельный тест таймаута |
| Файл инструмента | 1 MiB | явная ошибка при превышении, base64 для сохранения любых байтов |
| Вывод команды | 65536 символов на каждый поток | дальнейший вывод дренируется, truncated=true |
| Артефакты | 64 MiB суммарно на сандбокс | ограничение tar и retained snapshots |

Размер tmpfs учитывается в RAM контейнера. SANDBOX_DISK ограничивает именно /work, а не суммарное место во всех writable mounts. Если задать /work больше RAM, сначала может сработать OOM. Существующий `.env` не перезаписывается автоматически — сверить свои настройки с `.env.example`.

Сеть — `none`, rootfs read-only, cap-drop ALL, no-new-privileges. Полная стресс-проверка CPU/RAM, adversarial-тесты и allowlist сетевых профилей остаются частью ЧП2; текущие проверки не доказывают полную безопасность Docker.

## Семантика исполнения и отмены

RunCommand получает argv, shell запускается только явно. cwd проверяется относительно /work. Файловые инструменты используют directory file descriptors и O_NOFOLLOW, не переходят через симлинки и не читают FIFO/devices. Это ограничение инструментов чтения/записи: произвольная команда видит файловую систему своего контейнера, но не файловую систему хоста.

В сандбоксе одна активная операция. Request_id дедуплицирует доставку HTTP; operation_id предотвращает повторный запуск команды даже с другим request_id. Несовпадающий payload возвращает 409. Result сохраняется один раз; при reconnect SSE может повторно доставить тот же event_id.

**Cancel/timeout останавливает весь контейнер.** Так исчезают и процессы, которые создали новую process group/session. Manager подтверждает, что контейнер не Running; если очистка не подтверждена, возвращается sandbox_error. После успешной отмены/таймаута /work потеряна, новый exec/collect запрещён; можно читать состояние/события и вызвать release. Для продолжения нужна новая сессия. Время таймаута — бюджет исполнения; остановка через Docker может дополнительно занять до 10 секунд при проблемах daemon.

Нормальное завершение команды сохраняет /work. Фоновые процессы после успешной команды разрешены до release, но collect вернёт `background_processes`, если они ещё работают: это предотвращает сбор файлов на фоне изменений. Release удаляет контейнер целиком независимо от активной команды.

Collect выполняется доверенным скриптом в сандбоксе: Docker archive API в проверенной конфигурации не предоставлял содержимое tmpfs. Manager повторно проверяет архив, убирает префикс work, сохраняет его в памяти и отдаёт через авторизованный GET с size/sha256. Release удаляет артефакты.

## Очистка и восстановление

- Каждый динамический контейнер помечен `agent_harness.owner=<project>` и sandbox id.
- release удаляет контейнер и артефакты; повтор release безопасен.
- Idle TTL — 30 минут без активной операции, проверка каждые 5 секунд.
- При SIGTERM manager удаляет контейнеры своего проекта; `stop_grace_period` — 45 секунд.
- После SIGKILL контейнер может пережить manager. При следующем запуске manager удаляет оставшиеся контейнеры по метке **до** ready. Если daemon недоступен, manager не становится healthy.
- Новый процесс получает новый server_epoch и отклоняет старые запросы. Продолжение старой команды после restart не обещается.
- `compose down -v` удаляет также auth-volume. Образы и build cache остаются обычным образом.

Файлы /work и архивы не сохраняются после release, но результаты команд (включая ReadFile и stdout) ещё хранятся в памяти до часа для чтения terminal result. Политику удаления содержимого результатов нужно согласовать с A-3.5 до работы с настоящими пользовательскими папками на ЧП2. Трейсы сейчас содержат идентификаторы и статусы; полного A-7 ещё нет.

## Граница выполненного этапа

Работает sandbox API и прямой вызов из контейнера харнеса. Агентный цикл и LLM-прокси добавлены в CP1-05; desktop-клиента пока нет. История операций — в памяти, API использует учебный HTTP-bootstrap; долговечное хранение, полноценный серверный стек и сценарии одновременного сбоя provision/shutdown требуют дальнейшей работы.
