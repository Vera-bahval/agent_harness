# План до первого чекпоинта

Статус на 2026-11-04: каркас и документация подготовлены; runtime ещё не реализован.

**Цель:** из чистого клона поднять сервер, подключить клиента и провести реальную задачу по пути клиент → gateway → харнес → LLM-прокси / sandbox-manager → сандбокс. Затем воспроизводимо прогнать Б1–Б5 и показать результаты.

Источник требований: [ТЗ A](https://github.com/deeppavlov/agentic-course-itmo/blob/b42540f5215b4ad30820bdd0330c466ba19e19e1/projects/A-agent-runtime.md). Ниже — наш порядок работ и критерии готовности, а не дополнительные требования преподавателей.

## CP1-01. Зафиксировать основу

- [ ] Создать public-репозиторий и подключить рабочий Git. В текущей среде `.git` — read-only каталог без действительных метаданных; здесь `git init` не выполнялся.
- [ ] Зарегистрировать/сверить уникальность комбинации харнес × сандбокс × mount по правилам курса.
- [ ] Прочитать `docs/architecture.md`, принять или изменить предложенные ADR 0001–0004. Механизм mount и сессии — ADR 0005–0006.
- [ ] Выбрать первую доступную разрешённую модель, запросить доступ при необходимости; записать версию, индекс, дату проверки. Ключ держать локально.

Готово, когда выбран понятный путь реализации и решения объяснимы. Нет доступа к модели — можно продолжить CP1-02…CP1-07 с replay, но реальный прогон ЧП1 остаётся открытым.

## CP1-02. Описать протоколы v0

Файлы: `contracts/client-server.v0.schema.json`, `contracts/harness-sandbox.v0.schema.json` и примеры в `contracts/examples/` (создать на этом этапе).

- [ ] Клиент: подключение с токеном, создание/закрытие сессии, отправка сообщения, события, cancel, reconnect с последнего event_id.
- [ ] Харнес: provision, exec с RunCommand/ReadFile/WriteFile, события, ровно один result на operation_id, collect, release/cancel.
- [ ] Общие поля: версия, идентификаторы, таймаут/deadline; stdout, stderr и exit_code не смешиваются.
- [ ] Различить command_error, timeout, sandbox_error, transport_error; определить политику ретраев. Не перезапускать изменяющую файлы команду вслепую после потери ответа.
- [ ] Определить срок хранения operation_id и событий, поведение дубликата с другим payload, cancel/result race и запрос после restart.
- [ ] Положительные/отрицательные примеры валидируются по схемам; неизвестная версия отклоняется.

Готово: обе стороны могут независимо реализовать протокол по документам. Одна схема сообщений ещё не доказывает поведенческие инварианты — их проверяют в CP1-04…CP1-06.

## CP1-03. Поднять серверный каркас

- [ ] Исходники и Dockerfile для gateway, harness, sandbox-manager, llm-proxy; закреплённые зависимости и базовые образы.
- [ ] `/health` и реальные healthcheck, готовность зависимостей, читаемые логи старта.
- [ ] У каждого сервиса только нужные env-переменные; LLM_API_KEY только у прокси.
- [ ] Публичный порт только gateway. Управляющие API доступны только внутренним сервисам.
- [ ] Заменить заглушку `make up` реальной командой, добавить `make down` и проверить повторный запуск.

Готово: `docker compose up --build` поднимает здоровые сервисы. Здоровые HTTP-заглушки — только этот этап, не готовая среда агента.

## CP1-04. Реализовать сандбокс

- [ ] `sandbox/Dockerfile`: минимальные инструменты для Б1–Б5, непривилегированный пользователь.
- [ ] Manager: provision → exec → collect → release; отдельная временная `/work` на сессию.
- [ ] RunCommand возвращает раздельные stdout/stderr/exit_code; ReadFile и WriteFile работают в `/work`.
- [ ] Таймаут команды, cancel с остановкой дерева процессов, один финальный result; повтор release безопасен.
- [ ] Минимальная защита с первого запуска: без сети, без socket/ключей внутри сандбокса, CPU/RAM/PIDs, cap-drop, read-only root, no-new-privileges; отдельное место для временных файлов.
- [ ] Ограничение диска выбрать и проверить отдельно: переменная SANDBOX_DISK сама квоту не создаёт. Полная проверка A-5 — к ЧП2.
- [ ] Manager помечает создаваемые ресурсы и очищает их после сессии/сбоя. Динамические контейнеры вне compose не удаляются автоматически через down.

Готово: через протокол создать файл и прочитать его, увидеть ненулевой exit code, прервать зависшую команду и проверить отсутствие контейнеров/процессов после release. Отдельно проверить, что canary-секрет сервера не доступен агенту.

## CP1-05. Реализовать харнес и LLM-прокси

- [ ] Прокси: replay для CI и адаптер настоящего провайдера, таймауты и нормализованные ошибки/usage.
- [ ] Харнес: system + user + история tool calls/results → LLM → валидация → sandbox → наблюдение → следующий шаг.
- [ ] Реестр RunCommand, ReadFile, WriteFile; отсутствие локального fallback на subprocess в харнесе.
- [ ] Условия остановки: финальный ответ, max_steps, deadline, cancel, невосстановимая ошибка. Ограничить размер вывода инструмента.
- [ ] Выбор харнеса/модели через `configs/pairs/`; модель не меняется внутри прогона.
- [ ] JSONL-трейс: идентификаторы, операции, длительности, исходы, токены. Секреты редактируются/не логируются.
- [ ] Заполнить `docs/harness.md` реальными ссылками на код.

Готово: replay вызывает команду через сандбокс, получает результат и завершает цикл; реальная модель затем решает Б1.1 тем же путём. Ошибка инструмента возвращается модели как наблюдение, а не выдаётся за успешный ответ.

## CP1-06. Подключить клиента

- [ ] CLI: адрес сервера, токен, создание сессии, сообщение и чтение событий до финала.
- [ ] Gateway проверяет токен и принадлежность сессии; неверный токен отклоняется.
- [ ] cancel и reconnect по event_id; повторная доставка события не дублирует действие.
- [ ] Микросценарии против mock-сервера: подключение, сообщение, поток, отмена, обрыв.
- [ ] Описать запуск CLI в `client/README.md`; выбрать путь к desktop-оболочке на ЧП2.

Готово: из отдельного процесса клиента видны tool events и итог задачи. Локальный вызов функции харнеса не считается подключением клиента. CLI — наш минимальный ориентир ЧП1; если преподаватель ожидает GUI уже здесь, добавить минимальное окно подключения поверх того же API.

## CP1-07. Написать раннер БАФ

- [ ] Найти task.yaml, проверить обязательные поля и отсутствие дубликатов id.
- [ ] Для каждой задачи/повтора создать новую папку только из fixture; чекер и эталоны туда не копировать.
- [ ] Через штатный API создать сессию и отправить messages, дождаться завершения с общим таймаутом, collect итоговые файлы.
- [ ] Доверенный check.py запускать вне среды агента с ограничением времени; разобрать JSON `{pass, reason}`. Exit code 0 сам по себе не означает pass=true.
- [ ] В finally освободить сессию и временные ресурсы; сохранить ошибки checker/transport/timeout отдельно от неверного ответа.
- [ ] JSONL: task_id, repeat, pass, reason, tokens_in/out, seconds, outcome, pair, model_version, git revision, trace_id. Недоступный usage — null, а не выдуманный ноль.
- [ ] Проверить кейсы: правильный ответ, неправильный, файла нет, таймаут, сломанный чекер, cleanup после сбоя.

Готово: Б1.1 проходит на реальной паре; намеренно неправильный результат не проходит; артефакты лежат в `results/baf/`. Ручное создание answer.txt проверяет только чекер, не агента.

## CP1-08. Первая веха: пять простых задач

- [ ] Б1.1 — прочитать настоящий порт, не старый из комментария (пример уже есть).
- [ ] Б2.1 — найти файл с определением parse_date, записать относительный путь.
- [ ] Б3.1 — создать config.json по spec.md, проверить скрытой JSON Schema.
- [ ] Б4.1 — изменить только версию в разделе Install; остальное сравнить побайтно.

Для Б2.1…Б5.1 создать task.yaml, fixture и check.py. На каждый чекер проверить правильный и хотя бы один правдоподобный неправильный результат. Replay-smoke подтверждает работоспособность пути; содержательные чекеры с реальной моделью подтверждают качество.

Готово: пять простых задач проходят по одному разу; сохранены трейс и сырые результаты каждой.

| БАФ | Средняя | С подвохом | Что проверяет чекер |

- [ ] Оформить десять оставшихся задач по каталогу; расхождение Б3.3 уточнено в `docs/sources.md`.
- [ ] Проверить чекеры на положительных и отрицательных примерах.
- [ ] Прогнать 15 задач, один повтор, фиксированная пара и чистые сессии.
- [ ] Все неуспехи сохранить и разобрать: ошибка задачи/чекера, модели, харнеса или инфраструктуры. После правок повторить затронутые случаи, затем сохранить итоговый полный прогон.

Готово для нашего ориентира: 15/15 проходят содержательную проверку; если нет — на ЧП1 честно показать фактическую матрицу и причины. Один успешный прогон не означает доказанную устойчивость.

## CP1-10. Подготовить воспроизводимый показ

- [ ] README содержит действующие команды установки, сборки, клиента, тестов и БАФ.
- [ ] `make test-ci`: contracts + unit + UI + infra + smoke Б1–Б5 на replay, без доступа к провайдеру. Установка зависимостей/сборка образов — отдельная подготовка; offline относится к выполнению тестов.
- [ ] `make baf-cp1 PAIR=...`: 15 задач на реальной модели, один повтор; JSONL и summary согласованы. `make baf` остаётся финальным полным режимом с 3 повторами.
- [ ] Очищенная среда повторно поднимается; `docker compose down -v` не оставляет сессионных ресурсов благодаря реализованному lifecycle/cleanup manager.
- [ ] ADR соответствуют коду; docs/report.md содержит фактический результат и ссылки на raw data, без вымышленных метрик.
- [ ] Пройти сценарий: поднять сервер → подключить CLI → решить задачу → показать tool trace → запустить БАФ → показать матрицу → очистить среду.

## Сверка с формулировкой ЧП1

| Требование | Доказательство |
|---|---|
| Compose поднимает сервер | чистая сборка, реальные healthcheck четырёх сервисов |
| Харнес исполняет команды в сандбоксе | трейс tool call, результат в /work, изоляционные проверки |
| Протоколы v0 | две схемы, версия, примеры, контрактные тесты |
| Клиент подключается | CLI с URL/токеном, сессия и поток событий |
| Первые ADR | принятые решения с альтернативами и последствиями |
| Раннер БАФ, проходят Б1–Б5 | автоматический прогон, содержательные чекеры, JSONL и summary |
