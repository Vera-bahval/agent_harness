# Клиент, gateway и сессии: CP1-06

Работает путь CLI → gateway → harness → llm-proxy/sandbox-manager → сандбокс. [Запуск CLI](../client/README.md).

## Реализация

| Механизм | Код |
|---|---|
| Команды CLI, запросы, чтение SSE, курсор и скачивание | [client/cli.py](../client/cli.py) |
| HTTP, авторизация каждого маршрута, SSE и heartbeat | [GatewayHandler](../services/gateway/app.py) |
| Проверка схемы, epoch/expiry, дедупликация и владение | [Gateway](../services/gateway/runtime.py) |
| Создание сессии и сохранение истории/workdir | [Session / AgentService](../services/harness/runtime/agent.py) |
| Внутренние операции сессий | [harness app](../services/harness/app.py) |
| Генерация локального токена | [setup_client.py](../scripts/setup_client.py) |

Gateway принимает JSON POST /v0/requests и подписку POST /v0/events. Все v0-маршруты, включая архивы, требуют Bearer-токен; /health и /live доступны без него. JSON Schema проверяет запросы, ответы и исходящие события. Чужой session_id/artifact_id возвращает 404. Неверный токен — 401.

В session.create харнес сразу provision-ит сандбокс. Один run работает в сессии одновременно. После успешного run харнес сохраняет историю и тот же сандбокс; только session.close освобождает его. Ошибка или отмена приводит к очистке сандбокса и запрещает продолжение. Отдельный старый `/internal/runs` без session_id сохраняет поведение CP1-05: временная сессия на один run и автоматический release.

Gateway транслирует метаданные трейс-событий харнеса в run.started/tool.started/tool.finished/run.result. Тексты файлов, аргументы и provider keys не попадают в события. Финальный answer принадлежит пользователю и передаётся клиенту. Ошибки модели/бюджета отображаются в существующий класс protocol_error с отдельным code, сохраняя схему v0.

## Повторы, закрытие и restart

Повтор request_id + тот же payload возвращает сохранённый ответ. Другой payload — 409. Принятие запроса сериализовано внутри процесса; конкурентный повтор ждёт первого ответа, новое действие не запускается. Ответы хранятся до expires_at; затем старый запрос отклоняется. Потеря ответа клиента допускает один повтор с неизменными request_id/expiry.

Буфер событий — последние 10000 за час, номера возрастают отдельно в сессии. Cursor за пределами будущего — 400, утраченный — 410. Terminal result хранится отдельно от событий. Heartbeat — каждые 15 секунд. Состояние run можно получить отдельным run.get после разрыва.

Session.close отменяет активный run, ждёт его остановки и release; только затем подтверждает закрытие. Повтор close безопасен. При превышении бюджета close возвращается ошибка, освобождение нельзя считать подтверждённым. Idle сессии закрываются по TTL 30 минут с проверкой каждые 10 секунд; харнес имеет независимый cleanup для потерявшего gateway. Gateway хранит закрытые сессии и результаты ещё час. В памяти харнеса установлен предел 1000 запусков/сессий на процесс; длительный dev-сеанс может потребовать перезапуска.

При старте gateway предъявляет свой epoch харнесу через внутренний attach. Харнес закрывает сессии предыдущего gateway до готовности нового. Одновременно поддерживается один gateway. Если меняется epoch харнеса, активный монитор завершает клиентский run как unknown_outcome; новые действия отклоняются, требуется перезапуск gateway. После restart результатов в памяти нет; пересоздавать run автоматически с новым epoch запрещено.

## Collect и ограничения

Session.collect возможен в ready: snapshot из manager возвращается gateway, который хранит неизменяемый архив до close. Каждый архив ≤64 MiB, общий объём в памяти gateway ≤128 MiB. Скачивание проверяет владельца; CLI проверяет размер и SHA-256. После close архив недоступен.

Сервисы используют учебный ThreadingHTTPServer. Решение сохранено для локального ЧП1: ограничены тела, бюджеты, объём результатов, SSE и файловые операции. Для production необходим отдельный HTTP-стек/TLS и ограничения соединений; текущий сервер опубликован на loopback. Долгие операции синхронно занимают общий lock gateway — это ограничение пропускной способности, которое можно пересмотреть после корректного базового протокола.

Ограничения ресурсов: максимум 1000 сессий и 10000 кэшированных запросов gateway, максимум 8 активных run харнеса. Mount ещё не реализован; source_id допускает только зарегистрированные fixture (Б1.1…Б5.1 и empty). Desktop, удалённый mount, долговечное хранение и распределённая работа не входят в CP1-06.

CP1-07: session.created дополнительно возвращает pair_sha256, run_result — фактические model/mode. Это необязательные поля схемы v0 для совместимости; раннер проверяет их перед формированием отчёта.
